# RFC 0053 Owner Review — RFC Process And Proposal Quality

Reviewer: `rfc` (review manager and process owner)
Date: 2026-09-20
Review target: `docs/rfc/0053-lir-structural-verification-and-translation-validation.md`
Reviewed revision: `status: DRAFT`, `updated: 2026-09-19`, four landed slices

## Verdict

**REQUEST-CHANGES**

Scope note: this review covers RFC *process and proposal quality* only. It does
not re-audit line-level C++ correctness; `ir-backend` and `verification` own
that surface.

The design itself is sound and the four slices are genuinely landed: the
verifier and the validator exist under `compiler/lir/verify/`, share no producer
helper (carrier derivation is a deliberate file-local duplicate in
`mir-to-lir.cc` versus `translation-validator.cc`), are listed in the explicit
CMake source list, fail closed before `llvm::verifyModule`, and the two new
ztests pass (16 + 14 assertions, sanitizer build). The blockers below are
proposal-accuracy and lifecycle blockers, not architecture objections.

Blocking findings: **6**. Non-blocking (NIT) findings: **5**.

## Blocking Findings

### B1. The documented failure projection does not exist in the implementation

RFC section: `Reference-Level Design` → "Failure Projection" (lines 381-388),
`Acceptance Criteria` item 4 (lines 551-552), `Compatibility And Rollout`
(line 518), `Implementation Plan` step 1 (lines 564-565), `Operational
Readiness` (line 536).

The RFC states that both stages "project through the existing IR failure
algebra at phase `IrFailurePhase::LirVerification` (`0x0d`)", that a finding
"maps to `IrFailureKind::InvalidFact` with a closed detail record carrying the
`LirVerificationFaultKind` tag and contexts", and that the finding "renders
through the incident path".

None of this is implemented:

- `LirVerificationFinding` and `TranslationFinding` have **zero** references
  under `compiler/ir/diagnostics/`; no `IrFailureFact`, `IrOperationResult`, or
  `IrInvariantRejected` value is ever constructed from a finding.
- `IrFailureDetailKind` (`compiler/ir/diagnostics/ir-failure.h:91`) has exactly
  three alternatives (`None`, `InstantiationCycle`, `InstantiationBudget`).
  There is no record capable of carrying a `LirVerificationFaultKind` tag, and
  `legalDetail` (`ir-failure.cc:216`) admits nothing else.
- `compiler/lir/` contains no `IrFailure`/incident reference at all.
- The actual production path (`utils/zomc/zomc.cc:1547-1564`) formats a
  `zc::String` (`"Internal compiler error: LIR structural verification failed
  (fault N)."`) and returns it as an ordinary `NativeObjectResult` error. It
  never enters `reportSessionIncident()` / `renderCompilerIncident()`, and the
  fault tag is printed as a raw integer rather than a closed detail record.

Consequence: `IrFailurePhase::LirVerification` remains, as the RFC itself
acknowledges at line 382, a phase with **no producer**. The RFC is still
accurate on that narrow point, but the document as a whole describes a
projection that does not exist, so Acceptance Criteria 4 ("with an internal
incident failure") is unmet by the landed code.

Note this also creates a documentation drift obligation: the landed
`docs/design/ir/lir.md` (lines 47-49) and `docs/design/ir/lowering-and-verification.md`
(lines 133-140) repeat the same claim ("aborts emission through the
`LirVerification` failure phase ... as compiler incidents"), and
`docs/design/ir/` is owned by `spec-audit`, which is not a required owner.

Fixed looks like: either (a) extend `IrFailureDetailKind` with a
LIR-verification detail record, construct the `IrFailureFact` at
`LirVerification`/`InvalidFact`, route it through `reportSessionIncident`, and
document the registry `phase`/`kind`/`producer` keys — in which case the impact
row for `compiler/ir/diagnostics/ir-failure.h` (line 427) is correct as
written; or (b) rewrite the Failure Projection section, Acceptance Criteria 4,
Implementation Plan step 1, and the rollout sentence to describe the actual
typed-string internal-error rail, rename the stage from "failure projection" to
"internal error reporting", and delete the claim that the `LirVerification`
phase becomes live. Partial landing of the projection (types present, no caller,
no test) is not acceptable under the repository's "no unused placeholders"
rule and under `docs/rfc/README.md`'s acceptance gate on unused code paths.

### B2. Landed scope diverges from the document in three places, and the divergence is invisible

RFC sections: "Function correspondence" (lines 311-318), "Effect relation" table
(lines 342-356), "Repository Impact" (lines 425-432), "Acceptance Criteria" item
1 (lines 543-545).

The RFC specifies one `LirVerificationFinding` with a `stage` discriminator
(`Structural | Translation`) and one `LirVerificationFaultKind` enum carrying
both structural and translation tags. The implementation instead has two
independent types: `LirVerificationFinding` / `LirVerificationFaultKind` in
`lir-verifier.h` and a separate `TranslationFinding` / `TranslationFaultKind`
in `translation-validator.h`, with no `stage` field and no shared fault enum.

The RFC also specifies that the two multi-function LIR symbols
(`zom.caller`/`zom.callee`) and the three-function-with-leaf module are part of
the multi-function slice, and the Status History row for slice 3 is correct
that owner-matching landed. But the RFC's effect-relation table and fault-tag
paragraph are written as if the multi-function slice covers those shapes,
while the landed producer for the three-function module is selected by
whole-module shape matching in `zomc.cc` (lines 1468-1533) and the module
selector still resolves `Call` callee indices by *emission position*, which is
exactly the failure mode the RFC's "Module-level call integrity" paragraph
(lines 371-377) claims to eliminate. That is a design-implementation tension
worth recording, not a defect by itself.

The document was never updated for either divergence. Under `docs/rfc/README.md`
"An RFC may move to `ACCEPTED` ... The RFC does not preserve unused code paths"
and the repository's radical-refactoring rule, a status transition cannot be
recorded over a document that describes types that do not exist.

Fixed looks like: update "Placement And Types", "Failure Projection", and the
fault-tag inventory to describe the two landed types and their separate headers
(or collapse the two types in the implementation and update the RFC to match);
remove the `stage` discriminator from the described record if the two-type
split is kept; and state explicitly which of the two multi-function symbols are
produced by which slice.

### B3. The `CallCalleeMismatch` fault tag is declared in the same change that the RFC places it in a later slice

RFC section: "Placement And Types" (lines 243-249).

The RFC says `CallCalleeMismatch` "arrives with the multi-function slice", while
the Type Placement paragraph enumerates translation faults "landing in slices".
The implementation declares `TranslationFaultKind::CallCalleeMismatch = 0x09`
in `translation-validator.h` in the slice-2 change, before the multi-function
slice. This is an enum-value reservation ahead of a producer, which the
project's "no tag is reserved without a producer and a mutation test" rule
(the RFC states this rule itself, line 255) prohibits. It is a NIT in isolation
except that the RFC's own prose and the landed code disagree about when the tag
exists, so it is folded into B2's required rewrite.

Fixed looks like: state in "Placement And Types" that all nine translation tags
are declared in the first translation slice, with `CallCalleeMismatch` produced
only by the multi-function slice; or remove `CallCalleeMismatch` from the enum
until the multi-function slice lands it.

### B4. `Open Questions` cannot pass the ACCEPTED gate as written

RFC section: "Open Questions" (lines 596-605).

`scripts/check-rfc.py` (`_check_open_questions_for_acceptance`) requires that
when the RFC is `ACCEPTED`, every Open Questions bullet be a single `- ` line
that contains both the literal `non-blocking` and the literal `follow-up`.
The two entries currently are multi-line bullets and use "Non-blocking:"
without the word "follow-up". Simulated against the actual gate at status
`ACCEPTED`, this produces **eight** errors (two "must be non-blocking and
assigned to follow-up", six "must be None or a bullet list").

This is not a defect in the questions themselves — both are genuinely
non-blocking — it is a machine-readable-conformance defect that will block the
`REVIEW -> ACCEPTED` transition at the gate. A status-history row recording an
acceptance that the CI gate rejects would violate the ban on fabricated
governance transitions.

Fixed looks like: one line per question, each ending with an explicit
`Non-blocking; assigned as follow-up to <owner/tracker>.` — the required
frontmatter/status edit below gives the exact replacement text.

### B5. `discussion`, `decision`, and `tracking-issue` are still `TBD` after all four slices landed

RFC frontmatter: lines 16-19. Compare `docs/rfc/0048-...md` and
`docs/rfc/0052-...md`, which both bind these three fields to a tracking
document before review.

`docs/rfc/README.md` forbids an RFC from reaching `REVIEW` with `discussion` or
`tracking-issue` as `TBD`, and forbids reaching `ACCEPTED` with `decision` as
`TBD`. The RFC has already landed four implementation slices and recorded four
`DRAFT -> DRAFT` status-history rows describing them. That is an
implementation-before-review inversion: the repository cannot record a
`REVIEW` review round or an `ACCEPTED` decision over work that is already on
`develop`, and it cannot honestly record a `REVIEW -> ACCEPTED` transition
whose review window never happened.

Fixed looks like: create `docs/rfc/tracking/0053-lir-structural-verification-and-translation-review.md`
with a Discussion Record, Owner Review Matrix, and Decision Record in the
RFC 0052 tracker format; bind `discussion`, `decision`, and `tracking-issue` to
its anchors; and add the missing status-history rows in one change. `rfc` is
already the review-manager and one of the three required owners, so this review
round can be recorded honestly once the tracker exists.

### B6. `required-owners` omits the owner of two affected path families

RFC section: "Repository Impact" (lines 431-432).

Two rows name paths outside the owned surface of the declared owners:

- `docs/design/ir/` is owned by `spec-audit` in `.codex/subagents/manifest.yaml`
  (`docs/design/**`). The RFC assigns it to `ir-backend`. Every comparable RFC in
  this repository assigns `docs/design/**` rows to `spec-audit` (RFCs 0001,
  0004, 0005, 0006, 0007, 0008, 0010, 0011, 0013, 0015, 0016, 0017, 0018,
  0019, 0022, 0024).
- `docs/rfc/README.md` is owned by `rfc` (already a required owner), so that
  half of the last row is correct.

`scripts/check-rfc.py` passes today only because it verifies
`required-owners == Repository Impact` set equality, not path ownership. The
acceptance gate in `docs/rfc/README.md` is stronger: "The repository impact
lists every owned path family and affected subagent."

Fixed looks like: change the `docs/design/ir/` row owner to `spec-audit` and add
`spec-audit` to `required-owners`; or, if `ir-backend` is the intended
technical author of that note with `spec-audit` as a consulted reviewer, state
that explicitly and split the row so the owning subagent is still named.

## Non-Blocking Findings (NIT)

### N1. `requires` omits RFC 0048 and RFC 0013

Frontmatter line 13 is `requires: [10, 21, 47]`. The Motivation section leans
directly on RFC 0048 ("RFC 0048 is generalizing it", "as RFC 0048 replaces the
shape rails") and the Design section leans on RFC 0007/0013 evidence discipline
("RFC 0007 operational-budget discipline"). RFC 0048 is `ACCEPTED` and is the
RFC that owns the MIR structural-verification surface this RFC extends. Adding
`48` (and `13` if the ownership-proof independence precedent is intended as a
dependency rather than an analogy) makes the dependency graph honest. No gate
checks this today.

### N2. The prior-art citation for the Utah AArch64 translation validator is imprecise

Prior Art, "Translation Validation (Pnueli; LLVM AArch64 Translation Validator)",
lines 135-146. The work exists and is correctly characterized (Regehr et al.,
"Translation Validation for LLVM's AArch64 Backend"), but the RFC gives no
title, venue, or URL while the other three prior-art entries name their source
directly. The claim in the Motivation that pattern tests and byte-parity miss
mapping defects is exactly the paper's finding, so precision here strengthens
the argument rather than weakening it. Also consider naming the Pnueli-Siegel-
Singerman paper explicitly rather than as "introduced by Pnueli, Siegel, and
Singerman".

### N3. "Resulting LIR instruction count" budget is not stated as a rule

Drawbacks And Risks, "Validator brittleness as lowering generalizes"
(lines 455-459), and Budget And Termination (lines 408-419). The budget section
gives `O(F + B + S + E)` and `O(M + S + B)`, but the primary defense against
unaccounted instructions is the lockstep consumption rule. Stating explicitly
that "verification allocates no per-construct dynamic state beyond the two
linear scans and the derived slot set" would make the budget claim checkable.
Minor.

### N4. Slice 4 does not name the CLI surface of the new failure mode

Operational Readiness (lines 532-539) says "a validation finding names the fault
tag and both contexts, sufficient to locate the producer arm without rerunning a
debugger". The landed implementation prints only the fault tag as an integer and
never prints `mirContext` / `lirContext`, because the `String` rail carries no
context. Once B1 is resolved this resolves with it; noting it here so the fix is
verified against the operational claim rather than only against the type check.

### N5. One "legacy" adjective remains in the Alternatives section

"Byte-Parity Snapshots As The Correctness Mechanism" (line 497) says byte parity
"depends on the legacy producer it is meant to replace". The sentence is part of
a rejected-alternative argument, not a compatibility layer, so it does not
violate the "no dual code paths" rule. It does brush against the repository's
prohibition on "legacy/bad-old-way" comparative prose in design documents; an
RFC's Alternatives section is the one place where comparative framing is
legitimate, so this is a wording NIT only.

## Verified Claims (No Finding)

These RFC claims were checked against the repository and hold:

- `compiler/lir/verify/lir-verifier.{h,cc}` and
  `compiler/lir/verify/translation-validator.{h,cc}` exist; both `.cc` files are
  listed explicitly (not globbed) in `compiler/lir/CMakeLists.txt`.
- Independence from the producer holds at the include level: neither verifier
  header nor either `.cc` includes `compiler/lir/mir-to-lir.h`. Carrier
  derivation is genuinely re-implemented
  (`mir-to-lir.cc` `integerCarrierFor`/`boolCarrierFor` versus
  `translation-validator.cc` `integerCarrier`/`boolCarrier`, with a comment
  stating the duplication is deliberate).
- Fail-closed ordering holds: in `utils/zomc/zomc.cc` `buildNativeObject`,
  `LirStructuralVerifier::verify` runs at line 1547 and
  `TranslationValidator::validate` at line 1559, both before
  `translator.translate` at line 1566, which reaches `llvm::verifyModule` at
  `compiler/backend/llvm/llvm-translator.cc:407`. A finding returns before any
  object bytes are produced.
- No `ZOMxxxx` diagnostic is emitted: the failure is an internal error string,
  not a source diagnostic. (The *rail* is wrong per B1; the *classification* is
  correct.)
- Mutation coverage is complete against declared tags: 13/13 structural tags and
  9/9 translation tags each have a rejecting ztest. Positive coverage exists for
  every admitted single-function shape in `llvm-translation-test.cc`, and the
  two/three-function modules are asserted in
  `lir-translation-validator-test.cc` (two-function multi-overload) and by the
  `object-emission-cli` ctest (three-function, end to end).
- Both new ztests pass: `lir-verifier-test` 16/16, `lir-translation-validator-test`
  14/14, run directly on the sanitizer build.
- `object-emission-cli` passes end to end (19.95s) on the LLVM-configured build.
- Section order, frontmatter completeness, RFC index row, status-history
  transitions, and Mermaid fencing are correct: `python3 scripts/check-rfc.py`
  passes (53 proposals).
- Name and identity rules hold: `check-no-internal-versioning.py`,
  `check-ir-architecture.py`, `check-english-only.py`,
  `check-ownership-architecture.py`, and `check-diff-hygiene.py` all pass.
  `lir::Function.owner()` carries the MIR `identity::DefId` as specified, and no
  `V0`/`V1` internal naming or compatibility shim appears.
- Acceptance Criteria 1, 2, 3, 6, and 7 are satisfied by the landed tree.
  Criteria 4 and 5 are satisfied on a non-sanitizer LLVM build; criterion 5's
  "on the sanitizer preset" clause cannot be satisfied by the CI-visible
  `sanitizer` preset alone, because `ZOM_ENABLE_LLVM_BACKEND` defaults OFF there
  and `tests/CMakeLists.txt` gates `object-emission-cli`/`native-run-cli` on the
  backend. `verification` should confirm the combined
  sanitizer + `--emit=binary` lane exists before that criterion is recorded
  closed.

## Test Plan Gate Names (Correction)

The Test Plan (lines 577-594) and Acceptance Criteria item 7 (lines 558-560)
give two gate commands with non-existent flags:

- `check-rfc.py` takes **no** flags (use `python3 scripts/check-rfc.py`).
- `check-format.py` has no `--check` flag; the flags are `--auto-format` and
  `--path` (use bare `python3 scripts/check-format.py`, which is the
  authoritative "changed files are formatted" check).

`check-ir-architecture.py --check`, `check-english-only.py --check`,
`check-ownership-architecture.py --check`, and `check-diff-hygiene.py --check`
are correct as written. The `check-ir-parity.py` command in the Test Plan has
the right flag but omits the required `--zomc <path>`; the script errors with
"`--record` and `--check` require `--zomc`". This mirrors a Round-1
`verification` objection on RFC 0052 ("the test plan invoked a non-existent
`check-rfc.py --check`"), so it should be corrected rather than repeated.

# ZOM Compiler Plan - 2026 Q4 (October - December)

> Planning window: **2026-10-01 to 2026-12-31**.
> Authored: 2026-08-25 (during Q3). Owner: compiler team.
> Scope: one quarter. Prior and subsequent quarters live in sibling files under
> `docs/plan/` (e.g. `2027-q1.md`). This document is the committed plan for Q4
> only; revise it in place during the quarter and archive it unchanged after.
>
> This plan is anchored to two hard constraints: (1) the RFC governance
> dependency chain (a status transition must precede any implementation it
> gates), and (2) on-disk technical reality verified against the source tree as
> of 2026-08-25, not aspiration. Every item is classified **reachable now**,
> **spec-blocked**, or **governance-blocked** so no work begins that a
> prerequisite forbids.

## Entry state (as of 2026-08-25, verified)

The frontend pipeline runs end-to-end:

```
Lexer -> Parser -> Binder -> Checker -> CheckedModule -> HIR -> Built MIR
```

- Built MIR emits `Return`, `Unreachable`, `Call`, `Goto` (0x04), `SwitchInt`
  (0x05) terminators and a `Comparison` (0x03) rvalue.
- Lowered shapes today: scalar local writes/transfers, nominal aggregate init
  and field writes, same-module direct calls with scalar-literal or parameter
  arguments, four-block diamond conditionals (primitive relational comparisons
  `Eq/Ne/Lt/Le/Gt/Ge` over two scalar operands, each a parameter or scalar
  literal), returned comparison results, and a minimal reducible `while` loop.
- Ownership rail (RFC 0007/0013) runs fail-closed; general region liveness,
  escape/capture production, and verified typestate remain in progress.
- **No backend:** no target LIR, ABI lowering, LLVM IR, object emission, or
  linking. ZOM cannot yet produce a native binary.

## Dependency chain (the spine)

```
RFC 0016 (REVIEW) --> RFC 0021 (DRAFT) --> LIR/LLVM backend --> native binary
                                     \--> RFC 0043 (link + executable)
RFC 0006 error-union ABI descriptor --> RFC 0046 (panic ABI) --> error-operator lowering
(semantic error-union shape already exists as RFC 0005 ErrorUnionShapeFact)
```

## Q4 OKRs (framing added 2026-08-26)

The G-numbered goals below are the concrete, per-commit work items and their
history. This section groups them into three Objectives with measurable Key
Results, so the quarter reads as outcomes rather than a task list. Every KR
carries an honest reachability class; a KR that a governance transition or the
environment forbids is written as **conditional** and is never reported "done"
by admitting a substitute (e.g. ambient LLVM). RFC statuses in this section are
the live on-disk values as of 2026-08-26 (0016 ACCEPTED, 0021 ACCEPTED, 0022
REVIEW, 0043 DRAFT), not the plan-start snapshot table above.

### O1 - Lower a meaningful language subset reliably to Built MIR
*Fully reachable now. This is the quarter's delivery center of gravity: it is
the only Objective that ships purely by writing and verifying code.*

- **KR1.1** G6a-2: a mutable-local write RHS may be a primitive binary
  operation. Requires generalizing the fixed 2-node-ids-per-write HIR stride.
- **KR1.2** G6b: a non-empty `while` body that mutates locals lowers to a
  reducible CFG. Requires redesigning `HirLoopStatement` to carry body
  statements.
- **KR1.3** RFC 0009 call-dispatch widening: at least one of multi-argument
  direct calls or method-receiver calls lowers end-to-end to Built MIR.
- **KR1.4** Publish a "constructs that lower end-to-end" inventory, each backed
  by a conformance corpus and fixed-id verifier coverage; report the count at
  quarter close against the entry-state baseline (measurable growth, not a
  vibe).

### O2 - Clear the two backend gates and reach first native output (AGGRESSIVE)
*Partially reachable; heavily environment-dependent. Chosen aggressive on
2026-08-26: pursue the first end-to-end MIR -> LIR -> LLVM path. The aggressive
KRs (KR2.3, KR2.4) are **conditional on KR2.1 clearing**; if the environment
cannot provide LLVM 22.1.8 they are blocked and will be reported blocked, not
worked around.*

- **KR2.1** G8: align the toolchain to LLVM `22.1.8` (from `19.1.5`) through the
  RFC 0016-accepted CMake/CI transaction. **May require environment
  provisioning outside this repo; ambient `19.1.5` must not be admitted.** This
  KR gates KR2.2-KR2.4. **Assessment 2026-08-27:** the pin is valid, not wishful
  - `llvmorg-22.1.8` is a real released upstream tag (object
  `e013073558445169e8732e25fa86e9913bfdd24e`). The environment provides only
  Homebrew LLVM `19.1.5`; no `22.1.8` is installed and (uid 1001, no root,
  network-restricted `brew`) it cannot be provisioned from within this session.
  KR2.1 therefore splits:
    - **KR2.1a (re-assessed 2026-08-27: NOT cleanly landable now):** the intent
      was an in-repo fail-closed CMake gate. Reading the accepted RFC 0016 CMake
      contract (that RFC's "LLVM build and CI contract") shows the gate is an
      **unconditional top-level configure gate** requiring exact `22.1.8`, whose
      positive fixture records a real resolved `llvm-config --version == 22.1.8`.
      Three facts make it non-landable here: (i) the frontend links no LLVM today
      (no `find_package(LLVM)` in any CMakeLists, no target links it), so wiring a
      mandatory gate in a `19.1.5`-only env breaks the frontend-only build used to
      verify every slice; (ii) the positive fixture cannot pass without a real
      `22.1.8`; (iii) it is RFC 0016 IMPLEMENTING-phase work, but 0016 is
      ACCEPTED-not-IMPLEMENTING and the IMPLEMENTING pointer is itself gated on
      `22.1.8`. An "opt-in/isolated" variant would either deviate from the
      accepted contract (drift) or be dead code until `22.1.8` (design principle
      #4). Conclusion: KR2.1a collapses into KR2.1b - it is blocked on the same
      `22.1.8` provisioning, not separately reachable.
    - **KR2.1b (DONE 2026-08-27 via from-source build).** The apt.llvm.org
      prebuilt hit a hard glibc floor (built for glibc 2.38+, host is Debian
      glibc 2.36: `llc` would not run, links failed on `__isoc23_*`), and the
      glibc-2.36-compatible GitHub tarball was network-unreachable. Resolved by
      building LLVM 22.1.8 from source ON this host, which is glibc-2.36-native
      by construction. A fresh isolated shallow clone of `llvmorg-22.1.8` (commit
      `ca7933e47d3a`) was configured X86+AArch64 Release with all optional deps
      off and built with `ninja -j52` (56-core host), installed to
      `$HOME/toolchains/llvm22`. Verified end-to-end: `llvm-config --version` =
      `22.1.8`; targets are exactly `X86 AArch64`; `llc --version` RUNS (rc=0,
      the exact tool that failed on the prebuilt); all 11 RFC-0016 components
      resolve; and a `verifyModule` program compiles, links, and runs (rc=0,
      system-libs reduced to `-lrt -ldl -lm`). `LLVM_DIR` =
      `$HOME/toolchains/llvm22/lib/cmake/llvm`. The earlier Swift `llvm-project`
      checkout was NOT touched (it is a dirty third-party tree). This toolchain
      is a local dev provision; CI still uses the RFC 0016 ubuntu-24.04/macos-15
      contract. With a runnable 22.1.8 present, KR2.1a and KR2.2-KR2.4 are now
      unblocked.
- **KR2.2** *(DONE 2026-08-27)* RFC 0016 -> IMPLEMENTING (`cb8e1e3b`, first slice
  landed as evidence) and RFC 0021 -> IMPLEMENTING (`f9c670bf`, implementation
  pointer set; both preconditions - RFC 0016 IMPLEMENTING and the provisioned
  22.1.8 toolchain - cleared). Real transitions with landed evidence; nothing
  fabricated.
- **KR2.3** *(DONE 2026-08-27, `fabf520d`)* Landed the first authorized RFC 0021
  slice: the LIR identity / carrier / layout / ABI / runtime-symbol /
  source-location / revision codec foundation (pure data, no live MIR consumer,
  no LLVM linkage). The live LirAlgebraCodec reproduces the RFC's documented
  56-byte empty-registry oracle + SHA-256 `03106c34...`; oracle, mutation, and
  fail-closed tests pass under the sanitizer build.
- **KR2.4** *(DONE 2026-08-27, `4f078d78`)* A scalar module initializer lowers
  MIR -> LIR -> LLVM IR and passes `llvm::verifyModule`, emitting
  `define i32 @zom.module_init() { entry: ret i32 42 }`. A minimal LIR model +
  `MirToLirLowering::lowerScalarInitializer` (fails closed outside the shape) feed
  a new `compiler/backend/llvm/` Pimpl shim - the sole TU including `llvm/...` -
  which builds the module in RFC 0021 deterministic order and publishes only on a
  clean verifier. Gated behind `ZOM_ENABLE_LLVM_BACKEND` (OFF = frontend
  unaffected, no LLVM linked). Object emission + linking (RFC 0043) remain out of
  scope this quarter, as planned.
- **KR2.5** *(added 2026-08-27; reachable now; strategy B - vendored self-managed)*
  Make LLVM 22.1.8 a *stable, reproducible, self-managed* dependency, following
  the Rust/Swift model for a serious self-hosted-IR-to-LLVM compiler rather than
  the lighter system-package model of out-of-tree tools. The exact-version pin +
  RFC 0016 fail-closed gate remain the reproducibility backbone; strategy B adds
  repository ownership of the exact source:
    - **Lock the exact LLVM source**, not just a version number: record
      `llvmorg-22.1.8` and its commit `ca7933e47d3a` in a repository lock (a
      pinned submodule or an explicit lock file), so the dependency is
      reproducible to the commit (Rust submodule / Swift monorepo discipline).
      This also leaves room to carry ZOM-specific LLVM patches later, which the
      system-package route forecloses.
    - **Dev provisioning**: a `scripts/` helper that builds the locked tag from
      source into a local prefix (e.g. `$HOME/toolchains/llvm22`), fixing
      `LLVM_DIR`. Building from source is required here anyway on heterogeneous
      glibc hosts (this host is Debian glibc 2.36; the apt.llvm.org prebuilt is
      glibc 2.38 and will not run), which is itself an argument for self-managed
      source rather than system packages.
    - **CI**: fixed `ubuntu-24.04` / `macos-15` runners; prefer a *cached
      prebuilt of the locked commit* (rustc `download-ci-llvm` style) over a
      rolling `apt install` / `brew install`, so CI uses the same commit-locked
      LLVM as dev and cannot drift. A dedicated backend CI job runs with
      `-DZOM_ENABLE_LLVM_BACKEND=ON` over the RFC 0016 discovery-gate fixtures
      (14/14) and the backend `llvm-translation-test`; frontend jobs stay OFF
      (fast, no LLVM), so `ZOM_ENABLE_LLVM_BACKEND` default-OFF remains the
      frontend contract while the backend dependency is stable where it is
      needed.
    System packages (apt.llvm.org / Homebrew) are acceptable only as a
    convenience fallback, never the source of truth - the locked commit is. This
    turns the current dev-only manual build into a commit-reproducible,
    CI-enforced, self-managed dependency, matching how Rust and Swift manage LLVM.

### O3 - Unblock the next wave through real governance and spec work
*Reachable now. G7 proved genuine per-owner review works and catches real
defects.*

- **KR3.1** RFC 0022 (flow-sensitive typing / null safety): REVIEW -> ACCEPTED
  via a real ten-owner review (no fabricated approval). **2026-08-27: HELD IN
  REVIEW on a genuine blocking defect (not fabricated to close).** A real review
  found RFC 0022 allocates diagnostics `ZOM4096`/`ZOM4097`/`ZOM4098` for
  null-safety and claims that range free, but the production registry
  `diagnostics-checker.def:150,152,154` now defines `ZOM4096
  ControlFlowSemanticsUnavailable` / `ZOM4097 VoidReturnSemanticsUnavailable` /
  `ZOM4098 ExpressionStatementSemanticsUnavailable`, with live conformance
  expectations asserting them (verified on disk). Accepting as written would
  double-allocate live, test-asserted codes. This is a design gap needing a
  normative re-allocation + snapshot re-review, not mechanical drift. A secondary
  producer-tag mismatch (`FlowRefinement` claimed after a non-existent
  `SignatureClassification = 0x15`) was also recorded. error-system OBJECT is
  recorded in the tracker; no owner was falsely marked approved. The stale
  recorded snapshot hash was mechanically reconciled to the current file
  (`1cbe543a...`). Follow-up: re-allocate the null-safety codes to a free range,
  fix the producer-tag reference, re-freeze, re-review.
- **KR3.2** RFC 0043 (link + executable): DRAFT -> REVIEW. **2026-08-27: HELD IN
  DRAFT (not review-ready).** RFC 0043's own Open Questions defer three
  substantive design decisions explicitly assigned "before REVIEW" (macOS SDK /
  Linux sysroot toolchain-discovery binding; which RFC 0010 failure rows cover
  linker-process failures; the native CI architecture lanes), all unresolved;
  and `discussion`/`tracking-issue` are both `TBD`. Structurally otherwise clean.
  A tracker `docs/rfc/tracking/0043-review-and-implementation.md` was created
  recording the hold, owner matrix, and blockers. Follow-up: resolve the three
  Open Questions and bind discussion/tracking, then DRAFT -> REVIEW.
- **KR3.3** Stretch-2 reachability verdict: a read-only investigation that
  decides do-or-drop on a checker-only `ErrorOperatorFact` slice. The verdict
  itself is the deliverable; a prior probe suggests raises-carrying calls are
  rejected before the operand type exists (likely unreachable), so this is not
  assumed shippable. **VERDICT 2026-08-27: DROP (code-traced).** The operator
  reaches the checker (parser accepts `?!`/`!!`; surface admission passes it via
  `isAdmittedErrorPostfix`), but the operand never has a formed error-union value
  type: `directCallableShape`/receiver-shape return none when `raises != none`
  (`body-checker.cc:1233,1387`), so a raising call forms no node-type fact;
  `ErrorUnionShapeFact` has zero producers (always `emptyFactMap`, verified at
  `body-checker.cc:3052`); the `ErrorOperator` production site
  (`body-checker.cc:2756-2785`) has no positive branch and always rejects
  (ZOM4032/ZOM4026 or a MissingRequiredFact invariant); and the cross-fact
  validator (`checked-facts.cc:1871-1904`) makes the two facts co-dependent and
  jointly unreachable. It is spec-blocked on RFC 0006 (an error-union value type
  + raising-call shape admission), a type-system increment far larger than
  G5/G6a-1 and governance-blocked, NOT a checker-only slice. The plan's earlier
  "authorized by RFC 0005" wording was inaccurate: RFC 0005 supplies the fact
  struct, not its producer.

### O4 - Toward a complete, usable toolchain (EXPANDED SCOPE 2026-08-27)

*Scope added mid-quarter on the goal "polish the compiler's capabilities to
completeness": end-to-end run, LSP, package manager, build tool, formatter,
debugger. This is a large surface; each KR is classified honestly against
on-disk reality, and - per this plan's governance rule - a feature whose RFC is
not yet IMPLEMENTING is written as "advance the RFC / land the reachable slice",
NOT "ship the feature", because implementation is governance-gated. Most of O4
realistically spans beyond Q4; the Q4 commitment is the reachable first slice of
each, with the rest scheduled into 2027 Q1.*

*Product-shape decision (2026-08-27): the toolchain is ONE front-end binary,
`zomc`, with subcommands (compile/run/build/test/add/fmt/...), matching Cargo,
Go, and SwiftPM. There is no separate package-manager or build-tool binary; the
empty `products/zomcrate/` and `products/zomforge/` placeholder directories were
removed. "Package manager" (KR4.3) and "build tool" (KR4.4) below name
capabilities of `zomc`, not distinct products. See
`docs/design/tooling/product-ecosystem.md`.*

- **KR4.1 End-to-end run (native binary).** *Backend-gated; RFC 0043 is REVIEW,
  not IMPLEMENTING; the backend has only the LLVM translator, no object emission
  or linking.* The `zomc run`/`compile` subcommands exist but have no backend
  behind them. Q4-reachable slice: extend the KR2.4 path with LLVM object
  emission (`TargetMachine::addPassesToEmitFile` -> `.o`) behind
  `ZOM_ENABLE_LLVM_BACKEND`, and drive RFC 0043 REVIEW -> ACCEPTED so linking is
  authorized. A real end-to-end `zomc run hello.zom` -> native executable needs
  RFC 0043 IMPLEMENTING (link + ToolchainClosure) and is the milestone this
  unblocks, not a Q4 guarantee.
- **KR4.2 LSP / IDE.** *Governance-blocked; RFC 0023 is REVIEW and no
  `tools/ide` or `tools/lsp` directory exists.* Q4-reachable:
  drive RFC 0023 REVIEW -> ACCEPTED via a real per-owner review, then land the
  first authorized slice (the IDE semantic-snapshot facade / document-version +
  cancellation core the RFC defines), not a full language server.
- **KR4.3 Package manager.** *Partially reachable; RFC 0012 is IMPLEMENTING and
  real `driver/package/` code exists (manifest, resolver, lockfile, archive,
  build-script plan).* Q4-reachable: continue the RFC 0012 implementation
  tracker's next slice (e.g. deterministic dependency resolution / lockfile or
  manifest surface end-to-end through `zomc`), with project-native tests.
- **KR4.4 Build tool.** *Overlaps RFC 0012 build-script + the driver.* Q4-reachable:
  a `zomc build` path that drives the package-compilation request through the
  existing driver to Built MIR for a multi-file package (frontend-complete build,
  no native emission yet - that waits on KR4.1).
- **KR4.5 Formatter.** *Governance-blocked; RFC 0044 is DRAFT.* Q4-reachable:
  advance RFC 0044 DRAFT -> REVIEW (author its open decisions from prior art),
  not implement the formatter.
- **KR4.6 Debugger.** *Governance-blocked; RFC 0045 is DRAFT and depends on native
  output (KR4.1).* Q4-reachable: advance RFC 0045 DRAFT -> REVIEW only; real DAP
  work is post-backend and belongs in 2027 Q1.

Honest overall note: O4 is a multi-quarter program. What Q4 can truthfully
deliver is (a) the reachable first implementation slice where the RFC is already
IMPLEMENTING (KR4.3, KR4.4) or backend-adjacent (KR4.1 object emission), and (b)
genuine RFC status advances for the governance-blocked ones (KR4.2, KR4.5, KR4.6,
plus RFC 0043 for KR4.1). "Complete toolchain" is the destination; these KRs are
the honest first steps, and none will be reported done by fabricating an RFC
transition or a feature that is not built and verified.

### Grading intent

O1 is the committed core and is expected to grade fully. O2 grades on gate
progress: KR2.1 (attempted, outcome reported truthfully) and, if it clears, as
far down KR2.2-KR2.4 as the cleared gate allows. O3 grades on the two
transitions plus a recorded verdict. O4 (expanded scope) grades per-KR on the
reachable first slice or the genuine RFC advance, NOT on shipping the full
feature - it is an explicitly multi-quarter program whose Q4 commitment is the
honest first step of each capability. A blocked conditional KR grades as
"blocked, cause recorded", never as failed-by-omission and never as done.

## Explicitly out of scope for Q4 (and why)

- **LIR/LLVM backend implementation.** Governance-blocked until RFC 0021 is
  ACCEPTED (targeted for REVIEW only this quarter). Q4 unblocks it; it does not
  build it.
- **Error-operator lowering (`?!` / `!!`) and RFC 0046 panic ABI.**
  Backend/governance-blocked. The semantic error-union representation already
  exists (`ErrorUnionShapeFact` over a canonical `Union`, RFC 0005); what is
  blocked is *lowering*: RFC 0006's error-union ABI layout descriptor is
  target-dependent (consumes RFC 0010 target selection), and RFC 0046 panic ABI
  is DRAFT with no approvers. A checker-only error-operator *fact* slice on top
  of the existing shape fact is authorized by RFC 0005 but is not required this
  quarter.
- **A3 drop materialization.** No MIR drop statement kind and no LIR/backend
  consumer; adding one now violates fail-closed. Deferred until the backend
  exists.
- **`as!` forced cast.** No parser support and no lowering target; adding it now
  is spec drift.

## Constraints this plan respects

- No forward compatibility, no version-suffixed contracts, fail-closed on
  unimplemented slices (`.codex/rules/design-principles.md`).
- No blocked IR or runtime artifact is published before its RFC authorizes it.
- Governance transitions are never fabricated; a DRAFT/REVIEW RFC is a real
  blocker, not a formality to route around.

## Follow-up work (beyond this quarter's committed goals)

verified fixed-shape-generalization pattern; the rest track the governance and
backend spine.

### Frontend, reachable now (no governance transition)
- **Nested / non-parameter arithmetic operands.** Comparison and arithmetic
  operands are a parameter/local reference or a scalar literal today. A nested
  binary operand (`a + b * c`) needs the checker and HIR to lower a binary whose
  operand is itself a binary node.

  admit two return arms; loops admit only an empty-body `while (param) {}`. Widen

  the back edge; the gap is producer-side MIR lowering).

  scalar-write shape exists; generalize it alongside the sequential-local shape.

  large checker workstream once it advances to ACCEPTED.
- **RFC 0009 dispatch widening.** Multi-argument calls, method dispatch, and

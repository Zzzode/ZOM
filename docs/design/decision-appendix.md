# Seven Foundational Decision Summary (Phase 2 Output)

## 1. D1 Error Channel Selection

**Recommended approach**: Option B -- syntactic sugar / validation rail over T|E union types (`raises E` unified and internalized as T|E), with user-defined Result enums serving as untagged discrete channels outside compiler specialization.

**Grammar compatibility**: Grammar and implementation naturally favor this approach. ANTLR ZomParser.g4:794 specifies `raisesClause: RAISES type` (single type that natively carries `A|B` unions). The schema-backed AST stores this as `FunctionDecl.raises_ty`, a `NodeId` pointing at a type expression; it does not define a dedicated RaisesClause or ErrorTypeList node. All examples in specification 11-error-handling.md (L65, L134) use `raises FileNotFoundError | ParseError` (pipe-separated union). These sources constitute a commitment to the position that `raises` is an annotation / validation rail over union types. Taking path A or C would require grammar and AST schema rewrites.

**Audit closure**: Directly closes the core P0 gaps across three audit reports without introducing additional abstraction layers:
(1) Resolves design audit Finding 18 (four-form non-unification, docs/reports/zom-design-audit-2026-06-23.md:1320-1395) regarding semantic conflicts among T? / T|null / raises E / Result and subtype combinatorial explosion. Option B performs a single canonicalization at the Checker entry point: T? -> T|null, nested unions flattened, deduplicated and sorted to produce a normalized SetType. `raises E` only affects the `errorTypes` set on `FunctionTypeSymbol` (equivalent to lifting error-tagged elements from the return value union as validation targets), without introducing new runtime value representations. User-defined Result enums remain nominal, do not participate in automatic normalization, and have clear boundaries.
(2) Resolves error audit Gap C (docs/reports/zom-error-system-audit-2026-06-23.md:259-281). `FunctionTypeSymbol` requires only the addition of a `Vector<TypeSymbol*> errorTypes` field. Binder/checker traversal over `FunctionDecl.raises_ty` adds union flattening and per-element lookup for `getErrorType()`, advancing `raises` from an AST annotation to a first-class citizen at the symbol layer.
(3) Resolves the applicable domain for `?!` / `!!` / `?:` operators raised in the error audit ETM series (L114, L130). Under Option B, the value of a `raises` declaration is precisely the T|E union, so all three operators act directly on unions containing error-tagged elements, with no need to distinguish between "raises-only" and "arbitrary union" applicability.
(4) Resolves specification inconsistency (17-grammar-reference.md:196 specifies `RaisesClause ::= 'raises' TypeList` with comma-separated list, while all three other sources use `|` unions). Option B directly rules that `|` unions constitute the sole normative representation; updating the TypeList reference in chapter 17 to Type resolves the decoupling with a single correction.

**User intent alignment**: Aligns with positions explicitly stated in the specification and the 2020+ industry consensus layering:
- Specification 11-error-handling.md:3 states "ZOM has no implicit error control flow" and L99 states that custom Result types are "not treated as error types by the compiler." Option B defines `raises` as compiler validation over the error subset of the return value union plus syntactic sugar entry point; it is neither an exception mechanism nor a new runtime channel, fully matching the specification.
- Design audit opposing arguments (L1360-1390) establish that four-form coexistence represents standard layering (syntactic sugar / explicit union / compiler validation rail / user free downgrade), universally adopted by Swift and Rust. Option B concretely instantiates these four layers as a unidirectional desugaring chain: user code (T? + raises E) -> AST (`OptionalTypeExpr` plus `FunctionDecl.raises_ty`) -> symbol layer (SetType = {T} union {null} union errorTypes, with T? = syntactic sugar and raises = validation tag).
- The 2020+ language consensus (Swift throws / any Error, Zig !T, Kotlin Result + null, TS `T | E`) centers on value semantics + compile-time annotation + optional forced unwrapping. Option B avoids the trap of Java checked exceptions (stack-based exceptions + declarative) while not forcing Rust-style Result generic nesting.

**Implementation cost**: Implementation cost comparison across three paths, measured by the effort required to pass the first 20 semantic test cases through the checker:
- A (raises as single channel, Result effectively eliminated): cost 2.0x. Requires rewriting two Result examples in 06-declarations.md (L227 alias and L368 enum) and deprecating them; adding a nominal tagging system for error types; `?!` and `!!` must operate exclusively on `raises` contexts with no interop with arbitrary T|E unions, requiring additional subtype branches.
- B (raises as syntactic sugar / validation rail over T|E, dual-track but unified at value layer): cost 1.0x. Requires only: (a) adding errorTypes field to FunctionTypeSymbol; (b) binder/checker traversal of `FunctionDecl.raises_ty` plus union flattening; (c) checker first pass performing canonicalization (T? -> T|null, union normalization, deduplication, error set extraction); (d) defining the `?!` expansion as specification text without adding new IR nodes. These four items constitute the P0 remediation path already identified in design audit Finding 18 plus error audit Gap C / Gap H.
- C (union-only, raises eliminated): cost 1.8x. Requires removing RaisesKeyword and the `FunctionDecl.raises_ty` schema payload across lexer / parser / AST; rewriting all examples and tests (raises.zom, 11-error-handling.md, 03-types.md:196 SafeParser); early-return semantics for `?!` require a new non-raises declaration mechanism to carry (otherwise callers cannot know which errors a function may return), effectively requiring introduction of an alternative "function metadata annotation" system whose cost is underestimated.
Key savings: Option B requires no new AST node types: `FunctionDecl.raises_ty` already carries the error type expression, and `UnionTypeExpr` already carries pipe-separated alternatives.

**Major risks and mitigations**:

- R1 -- tag ambiguity between error types and ordinary values within T|E unions. Mitigation: specification defines that instances declared with the `error` keyword carry a compiler-injected nominal tag (similar to Swift Error existential _typeDiscriminator), enabling deterministic determination of "error element status" during normalization. `?!` match expansion performs early-return only for error-tagged elements; non-error elements pass through the value channel. Written into the first subtype rule of the checker.
- R2 -- eco-system fragmentation caused by missing interconversion between custom Result enums and T|E unions. Mitigation: provided in the standard library prelude (not built into the compiler): (a) `Result<T,E>.fromUnion(u: T|E): Result<T,E>` and `u.toUnion(): T|E`; (b) `trait Try<Output=T, Error=E>` unifies types on which `?!` can operate (appendable to enums), guaranteeing that library authors who write `enum MyResult { ... } impl Try for MyResult { ... }` automatically integrate with `?!`. Aligns with Rust Try trait, avoiding the historical debt of Result / throws non-interoperability prior to Swift 5.
- R3 -- unfixed grammar inconsistency in the specification (chapter 17 TypeList comma-separated list versus `|` union in three other sources) amplified in user testing. Mitigation: as a direct action of the D1 decision, freeze 17-grammar-reference.md:196 to `RaisesClause ::= 'raises' TypeExpression`, removing all TypeList usage in the raises context; simultaneously remove the declared-but-zero-reference `RaisesClause` / `ErrorTypeList` SyntaxKind entries in kinds.h (dead code identified at audit L199), aligning all layers in one pass.
- R4 -- semantic drift between `Future<T raises E>` and `T raises E` dual tracks during async fn extension. Mitigation: under Option B semantics, `raises E` always denotes declaration of the error subset of the return value union and carries no additional asynchronous semantics. Therefore `async fn f() -> T raises E` is naturally equivalent to `fn f() -> Future<T> raises E` (synchronously returns a Future; on the value domain E does not merge into Future's Output but instead follows the same function return union path as synchronous raises). `await` performs only Future<T> -> T value unwrapping without reinventing the error channel. Written into the D1 alignment clause of the concurrency specification chapter (existing design v1 under docs/concurrency/).

**Rejected approaches**:

- Option A -- raises(E) single-channel unification (union and Result eliminated or attenuated) -- bidirectionally conflicts with implementation and specification examples. Parser stores raises' E as a normal type-expression `NodeId` (including `UnionTypeExpr`); the path "raises is an independent channel whose E does not participate in T|E unions" requires reinvention of an error wrapper at the IR layer. Meanwhile the general union section in specification 03-types.md (L89-110) and the Result example in 10-enumerations.md already exist; retraction would entail 30+ page-level specification rollbacks. Additionally, Option A forcibly separates error types from ordinary values, meaning the match expansion `when E(e) => { return e; } when v:T => { v; }` (core of raises semantics) requires two type system views (error-world versus value-world), with subtype algorithmic complexity approaching Option C.

- Option C -- union-only (removes raises keyword) -- three fatal points: (1) Loss of compiler-validated error propagation boundary: without raises there is no enumerable error set on function signatures; `?!` subset checking (E_in subset of E_out), match exhaustiveness checking, and cross-module API comparison all require manual user annotation, degrading to the unchecked level of Go `if err != nil`. (2) Wasted implemented assets: lexer already tokenizes RaisesKeyword, parser writes `FunctionDecl.raises_ty`, the AST schema has a stable raises payload slot, and tests already have raises.zom baselines. (3) Specification 06-declarations.md declares `error` as a first-class type constructor (full chapter at L393-432).

## 2. D2 Concurrency Safety Marker System

**Recommended approach**: CONDITIONAL GO -- retain the direction of three core markers, subject to completion of seven mandatory corrections before implementation.

**Grammar compatibility**: Three mismatches at the grammar layer, severity HIGH:
(1) Design documentation consistently uses the `trait` keyword (section 7.1 `unsafe trait Sendable {}`), but SPEC chapter 09 defines only the `interface` keyword (`interface Drawable { ... }`), with standalone `impl I for T {}` blocks as the sole implementation path. Standalone `impl<T> Sendable for Foo {}` syntax, `negative impl` syntax, and `auto_trait` modifier -- none of these three exist in the current grammar.
(2) Design extensively uses built-in attributes such as `#[linear]` / `#[zom::runtime_only]` / `#[zom::scope_guard]`, but SPEC chapter 16 explicitly states "Attribute and annotation syntax is reserved for future language design".
(3) The `unsafe` keyword / syntax block does not appear in any SPEC chapter (chapter 09 interfaces, chapter 12 generics, chapter 14 memory); syntactic validity of `unsafe trait` and `unsafe impl` is zero.
Collectively: the design direction is correct, but its syntax vehicle is completely disconnected from the existing SPEC. Keyword naming must be unified before implementation, without violating NP-6 (only two new concurrency keywords: suspend and spawn). Recommended approach: reuse `interface` and extend modifiers without introducing the new `trait` keyword.

**Audit closure**: Of the ten hostile audit findings, five directly relate to this marker system (B.3 / B.8 / B.9 / waker dimension of B.10 / Linear path of B.5), none closed:
- B.3-AUD-DR-01 Scenario B (Critical): `Shared` lacks a negative impl for `UnsafeCell<T>`. This is the linchpin of soundness for the entire marker system -- the auto-trait mechanism would incorrectly derive `struct WrapCell { c: UnsafeCell<u32> }` as Shared, causing silent data races when shared across spawn boundaries as `&WrapCell`, rendering the trait system entirely unable to gate.
- B.8-AUD-CT-01 (High): the `spawn_scope implicit join` row in the cross-gating table marked "compile-time checked" actually relies on runtime information from the task-local scope stack; the compiler cannot statically prove this under lexical cross-function wrapping scenarios. The declaration is misleading.
- B.9-AUD-RL-01 (Medium): P10 lifetime gating requires HRTB (`for<'a> body: FnOnce(&'a Scope<R>) -> R`)-level borrow analysis, while the current type system possesses only basic lifetime inference; HRTB does not appear anywhere in the SPEC.
- B.10-AUD-RL-02 (Medium): the clone annotation for a single waker on Channel `send_ev/recv_ev` contradicts SuspendEvent single-shot semantics, fundamentally reflecting that if a Linear type permits clone (`send_ev.clone()`), the Linear one-shot constraint is semantically bypassed -- requiring explicit rules for "reference-counted wrapper + internal Linear downgrade".
- B.5-AUD-DO-02 (High): Linear resources are not fully cleaned on the Double-Panic path, proving that Linear's "exactly-once consumption" guarantee does not hold at the panic-unwind boundary and must be downgraded to "normal path compile-time 100% + unwind path linear_drop runtime fallback" with explicitly declared boundary conditions.

**User intent alignment**: The marker system aligns strongly with three direct demands from the user 1.0 specification:
(1) Section 9 P0-1 "absence of Send/Sync gating causes data races and use-after-free" -> Sendable/Shared correctly respond (migration table #8 keeps Gap-5 closure).
(2) Section 12 P1-3 "TaskHandle linear consumption undetermined" -> Linear plus #[linear] attribute correctly respond (migration table #12 replace).
(3) Section 3 Principle 3 "contract-driven sole suspension mechanism" -> NoInternalMutability / SuspendEventContract serve as auxiliary trait support.
One principle conflict exists: NP-6 "only two new keywords" conflicts with the three implicit new syntax constructs (`trait` / `unsafe` / `impl`) in the design (see grammarFits). Additionally, the user specification does not mention `auto_trait` / `negative_impl` at all; both are technical prerequisites for introducing the marker system and must be documented with complexity assessments.

**Implementation cost**: Implementing the marker system requires the compiler frontend to add seven independent subsystems, all currently empty shells:
(1) Trait solver (interface constraint matching + where clauses) -- depends on a complete generic system before work can begin.
(2) Auto-trait propagation engine (recursive closure derivation across struct / enum fields) -- approximately 2-3 KLOC of checker-level code.
(3) Negative impl parsing, conflict detection, and merge rules (RFC 105-level complexity).
(4) Closure capture classifier (three-way classification by-value / & / &mut + minimization analysis of capture sets) -- equivalent subset of Rust's NLL borrow checker.
(5) Flow-sensitive liveness analysis (active variable scan at suspend points) -- requires CFG construction + data flow iteration algorithm.
(6) Linear use-def chain checking (including partial move semantics: `let a = foo.a` must still track `foo.b`).
(7) Lifetime analyzer to at least the HRTB subset (P10 spawn_scope lifetime declaration confirmation).
Items (4), (5), (6), and (7) collectively constitute an equivalent implementation of approximately 40% of the Rust borrow checker's capabilities, representing 60-70% of the total type system complexity.
Based on current team velocity (parser/binder approximately 12 KLOC / 6 months): end-to-end marker system delivery requires 8-11 months, the single highest-cost item in the entire concurrency system.

**Major risks and mitigations**:

- R1 (Critical) Keyword naming conflict: design internally uses `trait` uniformly while SPEC uses `interface`. Without advance unification, AST nodes / diagnostic naming / documentation will be mutually incompatible mid-implementation. Must be finalized within 48 hours of project kickoff. Recommended approach: reuse `interface` (`unsafe marker interface Sendable` syntax, adding `marker` modifier plus `unsafe` keyword without introducing the new `trait` keyword).
- R2 (Critical) Missing negative impl for UnsafeCell invalidates system soundness: if B.3-B is not written into the specification body before the first line of implementation, the compiler will silently pass the most critical data race scenario. This issue was a CVE-level defect in Rust's pre-1.0 2015 history; ZOM has no reason to repeat it.
- R3 (High) Dual semantics of Linear checker at the panic-unwind boundary: normal path provides compile-time strong guarantee; exceptional path provides runtime best-effort. Without explicit documentation and downgrade to "bypassable within unsafe blocks", users will form an incorrect mental model ("Linear = always exactly once"), leading to resource leaks or double-free in FFI + panic combination scenarios.
- R4 (High) Philosophical conflict between auto-trait and existing OOP interface design: SPEC chapter 09 interfaces currently follow a nominal + class-implements OOP model (implements written inside the class, explicitly declared per class). Auto-trait is fundamentally structural (automatically derived by field structure). Coexistence of both under the same `interface` keyword requires explicit "split rules between marker interfaces and ordinary interfaces". The most typical conflict: `impl Bar for Foo {}` explicitly implements ordinary interface Bar while auto-trait Sendable is implicitly !Sendable because a field has `*mut u8`, invisible to the user at the class declaration point.
- R5 (High) HRTB capability gap: if spawn_scope implementation begins before the borrow analyzer reaches HRTB level, P10 degrades to runtime checking, the stated 18/20 compile-time trap coverage figure becomes invalid, and the overall externally-claimed "18 compile / 1 runtime / 1 sanitizer" matrix requires immediate revision to 16/3/1.
- R6 (Medium) False positive / false negative balance for cross-suspend lock checking (NoInternalMutability): liveness under lexical scope (simple implementation) incorrectly flags `drop(guard); suspend;` with explicit drop as ZOM8006; under flow-sensitive (correct implementation), complexity rises an order of magnitude and diagnostic messages are difficult to understand. A point of contradiction between user experience and correctness.
- R7 (Medium) Opaque propagation of `Movable` negative impl: a type negatively implements Movable due to OS TLS dependency, and aggregating structs automatically become !Movable; users cannot locate the cause after three levels of nesting. Diagnostics must output the complete negative impl propagation chain, similar to Rust's field-level expansion of "the trait Send is not implemented for *mut u8".

**Downstream binding constraints**:

The D2 marker system resolution binds the following five immutable constraints downstream; no subsequent concurrency subsystem design (runtime, scope, channel, FFI) may violate them:

[DS-1 Keyword constraint] The `trait` keyword must not be introduced as new. All marker semantics must be expressed by extending `interface` (new modifiers `marker` / `unsafe` / `auto`; implementation syntax unified as `impl InterfaceName for TypeName {}`, shared between interfaces and markers).

[DS-2 Atomic ordering constraint] Memory visibility guarantee across `Sendable` boundaries is a subset of C11 SeqCst semantics: the atomic enqueue operation of spawn (section 5.2 atomic push) and the atomic pop of worker task extraction naturally form a release-acquire pair; users require no additional fence. Document this guarantee to prevent excessive barrier insertion at the downstream FFI layer.

[DS-3 Linear non-bypass constraint] Linear type compile-time checking may be explicitly bypassed within `unsafe` blocks (`unsafe { forget(linear_value) }`), but the compiler must output the specific Linear type name and line number in the UNSAFE_USAGE diagnostic list. In pure safe code, Linear must maintain 100% compile-time guarantee.

[DS-4 Trap matrix transparency constraint] If R5 (HRTB gap) remains unresolved at implementation stage, P10 must immediately degrade from `compile` to `compile+runtime`, the public 20-trap matrix figure revised from 18/1/1 to 16/3/1, and displayed as the first entry in CHANGELOG. False advertising of compile-time coverage is prohibited.

[DS-5 B.3 precondition constraint] The compiler's first marker-supporting commit must include the `!Shared` negative impl for `UnsafeCell<T>` plus corresponding lit test (L03-bis: `struct X{ c: UnsafeCell<u32> }` captured by spawn via `&X` -> ZOM8002 error). Absent this test, the entire PR must not merge.

**Rejected approaches**:

- NO-GO: Abandon the marker interface system entirely in favor of Go-style runtime + TSan pure dynamic checking. Violates ZOM global NP-10 principle "explicit over implicit + compile-time over runtime". Compile-time trap capture in the 20-trap matrix drops from 18 to 3-4; P01 / P02 / P03 / P04 / P10 / P12 / P18 are all lost. The Go route costs "users must forcibly run 3+ TSan seed sets in CI + production data races remain UB", inconsistent with ZOM's positioning as a systems-level language for safety goals. Additionally, 10+ years of Go community experience prove that pure runtime checking cannot support non-GC + raw pointer systems programming scenarios (Send/Sync traits represent the core watershed of Rust's success).

- DEFER: Defer marker system implementation to v1.5; concurrency v1 implements only runtime + documentation conventions. Unsustainable. Absent Sendable/Shared gating at the spawn boundary means P01 data-race use-after-free is default behavior; the first concurrency release would be memory-unsafe. Once un-gated code forms an eco-system, re-introducing markers at v1.5 incurs breaking-change-level costs (Rust 2018 edition's async Send boundary tightening is a precedent, requiring a 2-year transition period). While ZOM pre-1.0 carries no backward compatibility promise, eco-system directional drift has irreversible repair costs.

- SIMPLIFY: Retain only Sendable + Linear two markers; delete Shared. Unsustainable. Deleting Shared means `&X` capture in spawn closures cannot statically distinguish safe from unsafe, forcing either blanket rejection of by-reference captures (mandating Arc wrapping + by-value capture) or blanket allowance (degrading to Go). The former cannot pass the section 11.1 parallel_map example -- `input[start..end]` as a `&[i64]` slice reference currently passes lawfully via Shared gating. Forcing migration to Arc<Vec<i64>> would degrade concurrency API ergonomics to the level of early Rust 2015 hand-written Arc<Mutex<...>>, falling too far behind the modern structured concurrency experience of Swift / Kotlin. The latter directly reverts to the NO-GO route.

- Downgrade Linear to must_use lint (Rust-like) without one-shot enforcement. Unsustainable. TaskHandle's linear consumption constraint is the sole mechanism for compile-time closure of P02 (zombie tasks). Downgrading to lint allows users to bypass with a simple `#[allow(dead_code)]`, undermining the structured concurrency nursery model. The historical lesson that Rust `JoinHandle` is not Linear is already proven: production code spawns then entirely forgets to join, causing silent task leakage and test flakiness. Linear is an explicit incremental value point of this design over Rust; downgrade loses architectural differentiation.

- Reuse existing Rust Send/Sync semantics for 100% compatibility and direct import of learning materials. Technically feasible, but would lose two critical differences: (1) Linear (Rust has no equivalent; JoinHandle only has must_use). (2) Zero function color interacts differently with Send boundaries -- Rust async fn Send is an associated bound on the Future trait; ZOM has no Future so Send boundaries must appear on spawn closure captures. Forcing 100% compatibility would import Rust's Pin/Unpin baggage. Correct strategy: "semantically align with Send/Sync; actively diverge on naming Sendable/Shared to avoid user assumptions of full equivalence, and explicitly document the differences."

## 3. D3 Spawn Boundary Lifetime Safety

**Recommended approach**: Option B: Lexical scope block plus spawn_scope built-in closure signature specialization (equivalent to compiler-built-in finite HRTB). Core mechanism: (1) spawn_scope follows ordinary library function signature `fun spawn_scope<R>(body: fun(scope: &Scope) -> R) -> R requires R: Sendable`; (2) compiler identifies via `#[zom::scope_guard]` attribute, injecting built-in borrow checking for the body closure that all captured reference lifetimes strictly terminate before spawn_scope returns (equivalent to a compiler-built-in specialization of `for<'a> FnOnce(&'a Scope<R>) -> R + 'a`, without exposing general HRTB syntax to users); (3) spawn static analysis boundary strictly limited to "within the lexical interior of the spawn_scope body closure"; cross-function propagation goes through runtime scope_stack validation (B.8 fix) with warnings at lint ERROR level; (4) Scope::drop generates a special "drop-with-suspend" frame, decoupled from ordinary RAII Drop to avoid the B.4 mutual exclusion conflict.

**Grammar compatibility**: Option B fully conforms to the current grammar. spawn_scope is a library function (no new keywords, complying with NP-6), depending only on compile-time built-in attribute recognition of `#[zom::scope_guard]`. Option A requires opening general HRTB syntax (`for<'a>` quantifier), undefined in grammar and requiring new lifetime syntax surface. Option C does not change grammar but violates NP-10.

**Audit closure**: Option B closes B.8 (clear lexical boundary with runtime stack check fallback), B.9 (built-in closure signature specialization bypasses user-side HRTB gap), B.4 (scope_guard attribute causes compiler to generate special "drop-with-suspend" frame at the drop point, decoupled from ordinary Drop). Option A closes B.9 but requires full HRTB. Option C cannot close P01 / P10 (ARC is orthogonal to data races).

**User intent alignment**: Option B provides optimal ergonomics: users need not hand-write HRTB signatures; closure captures infer automatically; writing `spawn_scope(fun(scope) { ... })` suffices. Option A requires users to understand `for<'a>` lifetime quantification, with a steep learning curve (the most complained-about point of Rust scoped_threads API users). Option C provides moderate ergonomics but implicit Arc clone per spawn leads to uncontrolled performance degradation.

**Implementation cost**: Option B has lowest cost: reuses existing closure borrow analysis plus new scope_guard attribute recognition plus scope_stack task-local runtime variable. Option A has highest cost: type checker / borrow analyzer extension for general HRTB (Rust took approximately 5 years to sound). Option C has moderate cost but introduces runtime overhead of atomic reference counting and cannot statically prove safety.

**Major risks and mitigations**:

- RISK-1 (Medium): bugs in the compiler-built-in spawn_scope closure specialization may allow scope references to escape. Mitigation: insert debug-mode runtime assertions `scope.borrow_escape_detected()` at all exit paths of the built-in analyzer; CI must run under det_sched mode; annotate the spawn_scope standard library implementation with `#[zom::trust_me]` while the compiler internally bypasses the user-side trust path.
- RISK-2 (Low): runtime validation for cross-function spawn (passing closures to helper functions that then spawn) may be disabled in release mode. Mitigation: runtime scope_stack validation is enabled by default; release mode removes only debug information such as scope_id strings; core id matching remains enabled; provide `-Z disable-scope-runtime-check` but forcibly mark it as unsafe.
- RISK-3 (Medium): inconsistency between lexical boundary and dynamic scope_stack may cause false positives on legal code. Mitigation: provide auxiliary attribute `#[zom::within_scope(scope_id)]` allowing users to explicitly declare that a function is called within a specific scope; the compiler may perform cross-function static propagation (linked with B.8 lint warnings; annotation silences lint).
- RISK-4 (High): mutual exclusion between Scope drop and panic unwind (B.4) if improperly implemented triggers resource leak or double-drop. Mitigation: first line of Scope drop entry executes `if in_panic_unwind() { goto fast_path_resources_only }`; fast_path performs no suspend, only calls `mark_cancelled_async()` on all child tasks (writes only CancelToken.requested atomic, no waiting), and records leaks to the Scope error aggregator.
- RISK-5 (Medium): developers may bypass lexical boundaries via `clone(Arc<Scope>)` or global static storage. ## 4. D4 Task Model: Stackful vs Stackless

**Recommended approach**: Stackful Segmented M:N (chained segmented stacks plus M:N work-stealing plus per-worker reactor). Rejected: Stackless Enum Generator (compiler splits each suspend point into enum variants as a state machine).

**Grammar compatibility**: The stackful M:N model fully aligns with step 7 of the specification section 5.1 suspend semantic 10-step expansion -- "save context (registers plus SP) and switch to scheduling loop" -- directly corresponding to setjmp/longjmp or callee-saved register push plus SP swap. No grammar EBNF changes required. The enum generator approach requires additional SSA-form deconstruction and enum payload encoding for cross-suspend active variables; while achievable at the IR layer, it produces double-copy semantics of "user stack -> enum payload -> restored stack", conflicting with Zero Color (NP-1) on debug information quality (debugger local variable stack frame chains break at each suspend point).

**Audit closure**: This review covers 7 of the 10 NP principles in the ZOM design specification strongly related to the task model (NP-1/2/3/4/5/8/10), and performs per-option verification over 12 of 20 traps directly related to stack / context management (P02 / P04 / P06 / P07 / P10 / P11 / P14 / P17 / P18 / P19 / P20 plus the runtime portion of P08), ensuring the recommended approach supports the existing trap matrix without compile-to-runtime degradation. Simultaneously compatible with the existing FiberStack plus jmp_buf / ucontext implementation path under libraries/zc/async/ with ZC_USE_FIBERS=1 (18 KLoC of existing code assets), reducing landing cost by approximately 60%.

**User intent alignment**: The user explicitly chose five principles directly bound to the task model in specification sections 1.0-8: (a) zero function color NP-1, (b) explicit suspension points NP-2, (c) contract-driven unique suspension NP-3, (d) Eager Task NP-4, (e) business-must-not-block-worker NP-5. The Stackful approach directly supports all five with zero compromises. The enum generator approach requires soft compromises at two points: (1) NP-5 (stack frame total size exceeding threshold may cause enum variant payload heap explosion without backpressure to the compiler) -- Stackful's segmented stacks plus guard pages naturally handle the 64KB-8MB range at runtime. (2) NP-8 single source of truth -- debug view inconsistency between enum generator lowering results and user-handwritten "equivalent functions" violates the spirit that "parser / type-checker / runtime / documentation / LSP derive from the same EBNF" (LSP hover information cannot display original stack frames at breakpoints after suspend).

Enum generator approach: requires implementing "coroutine state machine lowering pass" in the compiler -- basic block splitting per suspend point, active variable intersection analysis, enum variant generation, cross-block active variable renaming pass. **Major risks and mitigations**:

- R1 Stackful stack-switch performance: setjmp/longjmp approximately 30-60ns on aarch64/x86_64 (including callee-saved reg save/restore), with 3-10x per-switch overhead compared to stackless enum resume (function call ~3-10ns). ## 5. D5 Zero Function Color vs Explicit Suspend-Capable

**Recommended approach**: C. Hybrid approach (default zero color plus static derivability plus explicit annotation capability plus FFI/Drop boundary forced explicitness).

**Grammar compatibility**: Option definitions are strictly exhaustive and mutually exclusive: A = strict zero color (signatures unmarked; UB remediated via requires_executor compile-time lint); B = strict explicitness (signatures force suspend modifier, eliminates UB but splits the ecosystem); C = default zero color plus derivable plus explicit override (hybrid, eliminates FFI boundary UB without forcing full signature pollution). Three options cover the complete industrial design spectrum from Go/JDK21 style (A) to Zig/Rust style (B) to Swift 6 style (C), no omissions.

**Audit closure**: This decision resolves the core contradiction between zom async canonical design section 3 NP-1 (zero color principle) and Appendix B.1 AUD-FC-01 (hostile audit identifying silent runtime boundary violations). Hostile audit concludes: the NP-1 claim of "caller imperceptibility from signatures" is a direct UB crash path at the bare OS thread to ZOM runtime boundary (no scheduling loop to switch to, task-local scope stack is empty, CancelToken does not exist), and zero color makes it impossible for callers to statically detect accidental invocation of suspend-containing library functions in any impl Drop (section B.4). ## 6. D6 Attribute Namespace Plus Minimal Attribute Set

**Recommended approach**: Two-axis namespace plus three-tier concurrency minimal attribute set scheme. Namespace axes: lang (compiler built-in / no import / reserved names, v1 must recognize), std (standard library level, requires import std.attr, compiler only reserves names without semantic checking), vendor (third-party / FFI, must use reverse domain prefix such as com_example::, compiler performs no semantic gating). **Grammar compatibility**: Zero conflict at grammar level: in current grammar-reference and ZomLexer.g4, @ is unoccupied by any production (only chapter 16 declares it reserved for future attribute syntax); # is unused as any operator or prefix. **Audit closure**: Directly closes the ungapped-position problem for at least 11 of 44 audit findings: high-5 (unsafe escape hatch corresponds to lang::unsafe); high-11 (Send/Sync trait declaration entry corresponds to lang::auto_trait plus lang::negative_impl); high-14 (cancellation propagation static gating corresponds to lang::cancel_safe); info-43 (concurrency diagnostic code trigger points correspond to checker entries for all 5 Tier-1 attributes); medium-22 (actor default non-reentrant plus opt-in attribute corresponds to lang::actor::non_reentrant / reentrant); high-18 (async and raises interaction gating corresponds to lang::must_use checking on Future return values); medium-16 (unsafe operation boundary corresponds to lang::unsafe boundary declaration on functions); medium-17 (spawn_blocking annotation entry corresponds to lang::spawn_blocking); high-8 (Pin attribute entry for self-referential structures with cross-await borrowing corresponds to lang::pin); medium-11 (task-local and Send barrier corresponds to lang::send_bound); plus the actor default-non-reentrant opt-in attribute requirement in .agents/subagents/concurrency.md Review Checklist item 7.

**User intent alignment**: Fully satisfies both demands: namespace layering plus concurrency minimal attribute set. The key value of the three-tier design lies in minimality: Tier-1 has only 5 items, serving as preconditions for all concurrency semantics (without unsafe there is no FFI escape hatch; without auto_trait there is no Send/Sync static checking; without must_use there is no Future / JoinHandle discarded result diagnostics). **Major risks and mitigations**:

- R1 Dependency risk: phase 0 TypeChecker skeleton is a single-point blocker for all subsequent work. If phase 0 extends beyond +50% (i.e., from 1.5 person-months to 2.25 person-months), all subsequent phases are delayed synchronously. Mitigation: phase 0 split into three independently deliverable sub-milestones (M0a: Checker skeleton plus Driver integration approximately 0.5 person-months; M0b: Diagnostic Registry unification approximately 0.4 person-months; M0c: Driver topological sorting plus Export flag writing approximately 0.6 person-months). Each milestone completion has corresponding green-bar tests (Checker empty run does not crash, 10 test diagnostic codes register and query correctly, topological sorting 3-node DAG outputs correctly). Any stuck sub-milestone does not affect parallel advancement of the other two.
- R2 Interface drift risk: the 3-system interface contracts defined in phase 1 (error -> Checker "validate raises subset" API, concurrency -> Checker "check spawn capture types" API, module -> Checker "query symbol export mark" API) may be found to have insufficient parameters during phase 2 cross-implementation. Mitigation: all phase 1 contract interfaces use "parameter struct plus return Result" pattern rather than scattered parameter lists; struct fields expand via Option<T> when added in phase 2, without modifying old callers. Simultaneously each interface ships with 1 minimal contract test; phase 2 interface modifications must simultaneously update contract tests, guaranteeing backward compatibility.
- R3 Concurrency runtime and zc library executor architecture conflict risk (audit risk items M-11 / M-19): zc library's current "per-thread EventLoop plus Executor point-to-point delivery" model has architectural incompatibility with the M:N work-stealing model required by the design document. Mitigation: insert a dedicated architecture validation spike at the end of phase 1 (end of 4th person-month): run 10 core tests from zc library async directory against the new M:N Runtime. Pass rate <70% triggers architecture fork decision -- either encapsulate an Adapter layer over zc library (preserving zc API unchanged, internally bridging to new Runtime) or mark zc library's async directory globally deprecated, migrating all user code to new Runtime (ZOM global design principle #3 Radical Refactoring supports this choice).
- R4 Cross-module raises subtype rule dispute risk: the error x module cross boundary most likely to produce design divergence is "module A imports function f() raises E1 from module B, wrapped within module A as g() raises E2 -- whether E1 must be a subset of E2". Rust has no corresponding mechanism; Zig's error sets have different semantics; this belongs to the category "no mature best practice to copy directly" (violating design principle NP-1). Mitigation: before phase 2 launch (no later than phase 1 month 3), convene a dedicated design review meeting requiring submission of at least 3 alternative semantic schemes, each accompanied by: (a) comparison of compilation results for 2 real code examples under that semantic, (b) implementation complexity estimate (line order of magnitude) for the error system and module system respectively, (c) migration cost assessment for semantic changes within 3 years. Principle NP-1 requires that "choosing a minority-position scheme must clearly state migration costs".
- R5 Test flakiness risk: after phase 3 concurrency system introduces TSan / deterministic scheduling seed mode, data races produce flaky failures in CI, with extremely high investigation cost. Mitigation: starting from phase 2, each PR touching concurrency x other system crosstalk must attach a stress test script of "3 different SEED sets x 100 loop iterations" as one PR gate; add a new entry "concurrency-related PRs must pass 3xSEED stress test" to the verification-agent checklist in AGENTS.md.

**Downstream binding constraints**:

1. Before phase 0 completion, sub-agents are prohibited from submitting code inserting custom check passes into the checkSources() main loop -- all temporary semantic check code must be written at the binder layer or injected via the Diagnostic Engine's "temporary lint code" mechanism; centralized migration to Checker's formal pass architecture occurs after phase 0 completion. Violators are marked blocker at the verification-agent stage.
2. During phase 1, the Symbol registration paths for the error system's error type, module system's module/package scope, and concurrency system's Sendable trait must uniformly pass through SymbolTable::registerSymbol() single entry; direct manipulation of the symbolsByName HashMap is prohibited. 3. FunctionTypeSymbol structure during phase 1 has exactly three fields that each subsystem is permitted to add: error system -> error_union: TypeHandle, concurrency system -> async_flags: BitField<AsyncFlag>, module system -> export_vis: Visibility. All three parties are prohibited from unauthorized addition of fields belonging to other subsystems' domains.
4. Diagnostic code number ranges are permanently allocated and written into docs/spec/chapters/zz_diagnostic_codes.md: ZOM0xxx = Lexer, ZOM1xxx = Parser, ZOM2xxx = Binder, ZOM3xxx = Checker-General, ZOM4xxx = Error-System, ZOM5xxx = Module-System, ZOM6xxx = Type/Generics, ZOM7xxx = Concurrency-Safety, ZOM8xxx = Concurrency-Runtime, ZOM9xxx = Driver/Crate/Internal. No subsystem may trespass into another system's number range.
5. Cross-boundary API changes require a "dual owner signoff" process: for example, if the error system wants to modify the interface signature of "validate raises subset", it requires simultaneous consent from the error subsystem owner and the concurrency subsystem owner (because the concurrency system's supervisor error aggregation also depends on this interface). During the current phase with no explicit owners, task-router-agent separately invokes the two corresponding sub-agents for independent review; both return approve before merge is permitted.
6. At phase 2 launch, a three-system cross-boundary test suite must be produced (no less than 15 test files), each file corresponding to a clear cross scenario: e.g., "cross-module spawn a function returning raises E" simultaneously covers module / concurrency / error three systems. This test suite serves as the core regression gate for phase 2 and phase 3; any PR breaking any test therein is treated as blocker.

(3) Approximately 28 of 170 findings are cross-boundary issues; without top-level demarcation, each requires cross-sub-agent coordination, coordination cost alone adds approximately 1.5 person-months.
